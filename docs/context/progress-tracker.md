Issuance is limited to 50 live pending invitations per project; the list is bounded to those pending invitations. Links are shared manually; this slice does not send invitation email.
- Acceptance uses verified Supabase Auth identity, exact normalized email, and a locked project transaction. Existing project members are not silently upgraded; authorized same-actor retries, concurrent same-key retries, and an accepted member revisiting an expired link recover the established result.

- `/login` signs in existing Supabase Auth users. `/signup` requires a name and creates an account, saving its normalized value as Supabase Auth `full_name` user metadata. `/signup/verify` accepts or resends a six-digit emailed code. The code uses one accessible, paste-compatible input displayed as six cells. The forms use the existing workspace palette; neither shadcn/ui nor Lucide was added. A request-scoped `AuthHandler` contains provider operations for later sign-in methods.
- `/` requires a confirmed, non-anonymous Supabase user on the server before rendering the blank canvas. Supabase SSR cookies and the Next proxy refresh sessions; sign-out closes canvas access. One-hour HttpOnly cookies remember the pending email and code send time for the verification UI. They are not session credentials.
- The verify page shows the code's ten-minute lifetime and a 60-second resend countdown. The resend Server Action blocks early submission even when the button is bypassed. Change clears the pending address and returns to `/signup`; a direct verify visit without a pending address also returns to signup, so no arbitrary email resend form is shown. Supabase Auth independently enforces the hosted 60-second email frequency and project email rate limit. The app maps provider rate limits to useful messages. A new code can be requested after the cooldown if mail was lost; no automatic resend occurs. The verify page uses conditional delivery wording because Supabase may mask signup attempts for existing confirmed accounts.
